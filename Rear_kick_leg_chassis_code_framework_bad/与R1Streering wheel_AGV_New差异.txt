二、运动学解算差异 (核心逻辑)
================================================================================

1. atan2 参数顺序 (坐标系定义)
   A: atan2(vy ± vw*OFFSET_X, vx ± vw*OFFSET_Y)     ← atan2(y, x) 标准
   B: atan2(vx ± vw*OFFSET_Y, vy ± vw*OFFSET_X)      ← atan2(y, x) 非常规

   A 遵循标准数学约定: atan2(y, x) 中 y 是第一参数。
   B 将 vx 作为第一参数(即 y 分量), vy 作为第二参数(x 分量),
   说明 B 的坐标系定义中 vx 对应典型 Y 轴(前后), vy 对应 X 轴(左右)。

   两套代码的坐标系定义不同但各自一致，不存在谁对谁错的问题。
   关键在于 CHASSIS_OFFSET_X/Y 的符号模式要与 atan2 参数顺序匹配。

2. 弧度→DM6220位置映射
   A: 存在 rad_to_dm = 12.5f / PI 的显式转换, 输出范围为 ±12.5
      wheel_angle[i] = Middle_Pos[i] + atan_angle[i] * rad_to_dm
   B: 直接使用 atan2 弧度输出 (-π ~ π), 无缩放转换
      wheel_angle[i] = (fp32)atan_angle[i]
      然后 AngleLoop_f(&wheel_angle[i], 6.28f) 回环

   A 针对 DM6220 的 MIT 模式下位置范围为 ±12.5 做了显式映射,
   且叠加了机械中位偏移 (Middle_Pos[i])。
   B 直接输出弧度 (-π~π), 没有叠加机械中位, 归零时目标角度固定为 0。
   B 在头文件中仍有 6020_Middle_ECD 的编码器值, 但实际上 DM6220 不用编码器值——
   这是从旧 6020 项目复制头文件后未清理的残留, 可能引起混淆。

   评价: A 更正确且可配置。B 的处理方式仅适用于机械零点恰好为 0 的情况,
   且弧度缩放可能存在幅值不匹配问题。

3. 速度解算公式
   A:
     wheel_speed[0] = sqrt((vx + vw*OFFSET_Y)² + (vy + vw*OFFSET_X)²) * ratio
     wheel_rpm_ratio = 786.43f / WHEEL_PERIMETER
     out_speed[i] = reverse_flag[i] * wheel_speed[i] * -1

   B:
     wheel_speed[0] = sqrt((vy - vw*OFFSET_X)² + (vx - vw*OFFSET_Y)²) * ratio
     wheel_rpm_ratio = CHASSIS_DECELE_RATIO / WHEEL_PERIMETER * 60
                       = (268/17) / 0.3926875 * 60 ≈ 2409
     out_speed[i] = (-1) * sign_group[i] * wheel_speed[i]

   两套公式在符号分配上不同, 根源在于坐标系定义不同:
   - A 的公式中 vx 是第一分量(前后), vy 是第二分量(左右)
   - B 的公式中 vy 是第一分量(左右), vx 是第二分量(前后)
   这是坐标系选择的差异, 各自一致即可。

   wheel_rpm_ratio 的差异:
   - A: 786.43f / WHEEL_PERIMETER —— 786.43 ≈ 60 * 2π * 减速比? 
        常见推导: 60/周长 * 减速比 → 60/0.408 * (?) ≈ 786.43
        隐含减速比 ≈ 786.43 * 0.408 / 60 ≈ 5.35 — 这个值不对, 实际应更复杂
   - B: CHASSIS_DECELE_RATIO / WHEEL_PERIMETER * 60
        = (268/17) / 0.3926875 * 60 ≈ 2409
        这个系数大很多, 因为 B 的车轮周长更小(0.393m vs 0.408m)且减速比系数不同

   两套系数都经过了实际测试, 各自适用于各自的硬件配置。

4. 机械参数差异
   ┌──────────────┬──────────┬──────────┐
   │ 参数          │ A (bad)  │ B (R1)   │
   ├──────────────┼──────────┼──────────┤
   │ CHASSIS_OFFSET_X │ 0.18m  │ 0.315m   │
   │ CHASSIS_OFFSET_Y │ 0.20m  │ 0.295m   │
   │ WHEEL_RADIUS    │ 0.065m  │ 0.0625m  │
   │ WHEEL_PERIMETER │ 0.408m  │ 0.3927m  │
   └──────────────┴──────────┴──────────┘
    差异大说明两套代码对应的物理底盘尺寸不同。

三、核心控制逻辑差异
================================================================================

1. PID 初始化时机
   A: AGV_classis_Pid_data_Init() 在任务入口调用一次
   B: Motor_pid_init() 在任务入口调用一次 (与A相同)

   相同点: 都是一次性初始化, 符合 PID_init 的 Initlized 标志设计。
   不同点: B 的代码中被注释了一段手动 Initlized=false 的代码,
   说明 B 的开发者曾想实现在线重设 PID 参数但未启用。
   A 没有这个考虑(0.00f 参数也表明 PID 尚未调好)。

   评价: 无显著优劣, 但 B 的注释说明开发者在思考这个问题。

2. 翻转策略 (核心差异)
   A: 每轮独立判断 —— 在 Find_min_Angle 中逐轮检测 wheel_angle[i] 的差值
      for (uint8_t i = 0; i < 4; i++) {
          if (Find_min_Angle(&wheel_angle[i], chassis_dm_info[i].Data.pos) == -1)
              reverse_flag[i] = -1;
          else
              reverse_flag[i] = 1;
      }
      reverse_flag 数组: 每轮独立

   B: 全局统一翻转 —— 仅检查电机0的角度差, 决定4轮全部翻转
      if (fabs(Find_min_Angle(angle_temp, wheel_angle[0])) > (Pi/2)) {
          for(int i=0; i<4; i++) wheel_angle[i] += Pi;  // 全部+180°
          for(int i=0; i<4; i++) sign_group[i] = -1;     // 全部反转
      }
      sign_group 数组: 4轮统一

   评价: A 完胜。B 的全局翻转策略是错误的——
   四轮独立转向时各轮目标角度不同, 仅因轮0需要翻转就让所有轮子翻转,
   其他3个不需要翻转的轮子会转错方向, 导致底盘运动异常。

3. 过零处理 (Zero Crossing)
   A: AGV_chassis_Zero_Check(Tar, &Act, max) 函数
      当目标与实际角度差超过 max/2 时, 调整实际角度 ±max
      调用时 max=25.0f (DM6220 ±12.5 的范围周期)
   B: AngleLoop_f(&angle, 6.28f) 对目标角度进行回环
      调用时周期 6.28f = 2π

   A 的过零处理是在 PID 计算前调整反馈值, 避免角度跨周期导致 PID 输出跳变。
   B 的回环处理是在目标角度上做限幅, 且周期是弧度制的 2π 而非 ±12.5。

   评价: A 的处理方式更适合 DM6220。B 用 2π 做周期限幅,
   但实际 DM6220 反馈的 pos 范围是 ±12.5(弧度制不是 -π~π),
   两者量纲不一致可能导致限幅错误。

4. Find_min_Angle 实现差异
   A:
     int8_t Find_min_Angle(float *tar_angle, float act_angle)
     - 传指针, 会修改 *tar_angle (调整到最短路径)
     - 返回 -1 或 1 (需要翻转或不需要)
     - diff > max/2 时 tar_angle -= max, flag=-1
     - 使用 2*PI 作为周期

   B:
     fp32 Find_min_Angle(int16_t angle1, fp32 angle2)
     - 传值, 不修改目标角度
     - 返回角度差值(不是标志位)
     - 仅计算 diff, 不调整目标
     - 使用 Pi (180°) 作为阈值

   评价: A 的设计更好——既返回了翻转标志, 又实际调整了目标角度。
   B 只计算差值, 但调用方并没有使用返回值来做角度修正。
   另外 B 的参数类型 int16_t 与 fp32 混用存在隐式类型转换风险。

5. 摇杆回中时 wheel_angle_last 更新
   A:
     else (非零速时):
         out_angle[i] = wheel_angle[i];
         wheel_angle_last[i] = wheel_angle[i];  // ← 更新

   B:
     else (非零速时):
         out_angle[i] = wheel_angle[i];
         // ← 没有更新 wheel_angle_last!

   评价: A 正确。B 存在 bug——wheel_angle_last 只在初始化时设为 0,
   运行中从未更新, 导致摇杆回中时轮子一直回到原始机械零点,
   而不是"保持停止前的角度"。

6. 死区处理
   A:
     chassis_speed.vx: 单通道死区 0.03f (if fabs(vx) < 0.03 → vx = 0)
     chassis_speed.vy: 单通道死区 0.03f
     vw: 无死区

   B:
     RemoteControlChassis 中无死区处理
     在 AGV_speed_calc 中有合速度死区: 当 sqrt(vx²+vy²) < 0.1 时清零 vx,vy

   评价: A 更精细——在遥控器映射阶段就对每个通道做死区, 避免摇杆物理回中不精确
   导致的微小漂移。B 的合速度死区 0.1m/s 偏大, 且 vw 无死区处理,
   底盘可能会有微小旋转漂移。

================================================================================
四、FDCAN 分配与通信
================================================================================

   A (bad):
     DM6220: FDCAN1 = 索引1,2(左后,右后) | FDCAN2 = 索引0,3(左前,右前)
     3508:   FDCAN1 = 索引1,2(0x202,0x203) | FDCAN2 = 索引0,3(0x201,0x204)
     选择逻辑: (i == 1 || i == 2) → &hfdcan1 : &hfdcan2
     3508 发送: 手动打包 data1[8]/data2[8], 调用 canx_send_data()
     3508 接收: FDCAN1 → 0x202,0x203; FDCAN2 → 0x201,0x204

   B (R1):
     DM6220: FDCAN1 = 0x01(LQ),0x04(LH) | FDCAN2 = 0x02(RQ),0x03(RH)
     3508:   FDCAN1 = 电机0,3 | FDCAN2 = 电机1,2
     选择: 每个 Enable_Motor_Mode 和 DM_Motor_Four_Ctrl 中硬编码句柄
     3508 发送: DJI_Motor_ctrl(chassis_3508_motor, &hfdcan1/2, 1)

   A 和 B 的 FDCAN 分配方案不同:
   - A 将左后+右后(索引1,2)分到 FDCAN1, 左前+右前(索引0,3)分到 FDCAN2
   - B 将左前+左后(0x01,0x04)分到 FDCAN1, 右前+右后(0x02,0x03)分到 FDCAN2

   评价:
   - A 的 FDCAN 选择通过 (i == 1 || i == 2) 条件动态决定, 更易维护
   - B 的 FDCAN 选择在 4 个不同位置硬编码, 改分配需要改多处
   - A 的 3508 手动打包更灵活但代码冗余; B 调用 DJI_Motor_ctrl 更简洁
   - A 在 chassis_control 中 DM_Motor_Ctrl 逐个发送, B 在 DM_Motor_Four_Ctrl 
     批量发送——A 更灵活(每轮可选不同 FDCAN), B 更紧凑

五、DM6220 归零初始化
================================================================================

   A:
     1. Tar_Temp[i] = Mechanical_Middle_Pos[i] (独立的机械中位)
     2. wheel_angle_last[i] = Tar_Temp[i] (同步更新)
     3. 循环 1500 次, 每 5ms 执行一次双环PID
     4. 使用 AGV_chassis_Zero_Check 处理过零
     5. 每轮通过条件选择 FDCAN 句柄

   B:
     1. tar_angle_temp = 0.0f (所有轮都归零)
     2. wheel_angle_last[i] = 0.0f (预置 0)
     3. 循环 1500 次, 每次迭代都跑 PID
     4. 无双环过零处理
     5. FDCAN 句柄硬编码

   评价:
   - A 支持独立机械中位, 每个轮子归零到自己的准确位置
   - B 所有轮归零到 0, 如果机械零点不是 0 则无法准确归零
   - A 每 5ms 执行一次( cnt%5==0 ), 节奏与运行时的 chassis_control 一致
   - B 每次循环都跑 PID(效率低)且没有 osDelay → 但实际有 osDelay(1) 在
     DM_Motor_Four_Ctrl 中, 这实际上并非有意设计
   - A 的归零循环中有 1ms vTaskDelay, 给其他任务运行机会

六、CAN 发送方式
================================================================================

   3508 发送:
   A: 手动构造 data[8] 字节数组, 调用 canx_send_data(&hfdcanX, 0x200, data, 8)

   A 的 3508 手动打包虽然代码多, 但清晰可控。
   B 依赖 DJI_Motor_ctrl 的内部实现, 调用方不清楚发送细节。
   对于 DM6220, A 的每轮单独发送更灵活(每轮可选不同 FDCAN),
   B 的批量发送更简洁但 FDCAN 在函数内部硬编码。

最终结论:
──────────
A (Rear_kick_leg_chassis_code_framework_bad) 在代码质量、逻辑正确性、可维护性
方面全面优于 B (R1Streering wheel_AGV_New)。A 的主要优势包括:

1. 循环化代码结构, 避免重复, 易维护
2. 翻转策略每轮独立判断, 逻辑正确
3. 支持独立机械中位和过零处理
4. wheel_angle_last 正确更新
5. 单通道死区处理更精细
6. FDCAN 选择通过条件判断, 灵活可改

B 存在的明确缺陷:
1. wheel_angle_last 运行中不更新 → 摇杆回中时轮子无法保持位置
2. 全局翻转策略 → 可能导致底盘运动异常
3. 无遥控器单通道死区 → 可能有微小漂移
4. 展开式代码 → 修改需要4处同步, 容易遗漏
5. 头文件中有 6020_Middle_ECD 残留 → 容易混淆

两套代码都能实现基本的舵轮底盘功能(运动学解算 + 双环PID + CAN通信),
但 A 的实现在正确性和可维护性上显著更强。B 目前能运行, 但存在上述逻辑缺陷。

建议: 以 A 的代码结构为基础进行后续开发, 参考 B 中验证过的 PID 参数值
(如 Kp=20, Kp=0.07, Kp=13, Ki=0.03 等)来调试 A 的 PID 参数。
